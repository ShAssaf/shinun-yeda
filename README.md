# שינון ביוכימיה

אפליקציית תרגול למבחן. שלוש חבילות: קבוצות פונקציונליות, יסודות עיקריים וקורט, ועץ האיזומרים.

## מבנה

| נתיב | מה זה |
|---|---|
| `src/app.html` | **קובץ המקור.** כל האפליקציה בקובץ אחד — מנוע ציור מולקולות, מנוע חידון, סנכרון, תצוגה. כאן עורכים. התוכן המוטמע ב-`data/decks.json`. |
| `www/` | תוצר בנייה. `index.html` + `manifest.webmanifest` + `sw.js` + `fonts.css` + אייקונים. |
| `android/` | פרויקט Capacitor לאנדרואיד. תוצר של `npx cap add android` — לא עורכים ידנית חוץ מהגדרות. |
| `tools/` | סקריפטי בנייה (בלי תלויות חיצוניות). |

## פקודות

```bash
npm run build     # src/app.html + data → www/index.html
npm run fonts     # מוריד גופנים מ-Google ומטמיע ב-www/fonts.css (דורש רשת, פעם אחת)
npm run icons     # מייצר אייקוני PWA ל-www/icons
npm run serve     # שרת מקומי לבדיקה, כולל כתובת לטלפון ברשת
npm run sync      # build + העתקה לפרויקט האנדרואיד
npm run apk       # sync + בניית APK (דורש JDK 21 ו-Android SDK)
```

לאחר `npx cap add android` יש להריץ פעם אחת:

```bash
python3 tools/make-android-icons.py
```

`npm run apk` דורש את משתני הסביבה:

```bash
export ANDROID_HOME=/opt/homebrew/share/android-commandlinetools
export ANDROID_SDK_ROOT="$ANDROID_HOME"
```

התוצר: `android/app/build/outputs/apk/debug/app-debug.apk` (~4.2MB).
ה-APK חתום במפתח debug — מספיק להתקנה עצמית, לא לחנות.

## מנוע החזרה המרווחת

התזמון הוא **FSRS-6**. הנוסחאות והמשקלים הועתקו מקוד הייחוס
`open-spaced-repetition/py-fsrs`, לא שוחזרו מהזיכרון.

לכל כרטיס נשמר מצב זיכרון: `s` יציבות בימים (הזמן שאחריו הסיכוי להיזכר
יורד ל-90%), `d` קושי בסולם 1..10, ו-`due` מתי להראות שוב.

תשובה רב־ברירתית ממופה לציון 1..4 לפי נכונות ומהירות — מהירות משמשת
כאינדיקציה לביטחון, במקום דירוג עצמי כמו ב-Anki או ב-Brainscape:

| תשובה | ציון |
|---|---|
| שגויה | 1 — חוזר בעוד 10 דקות |
| נכונה, מעל 12 שניות | 2 |
| נכונה | 3 |
| נכונה, מתחת ל-4 שניות | 4 |

סבב מורכב לפי סדר: כרטיסים שהגיע זמנם (המאוחרים ביותר קודם), אחר כך
חדשים, ואז אלה שהכי קרובים להישכח.

`tools/smoke.mjs` בודק את האלגוריתם במפורש — ש-R(S,S)=0.9, שהאינטרוול
עולה עם הציון, שהצלחה מגדילה יציבות וטעות מקטינה, ושהמתזמן מקדים
כרטיס שהגיע זמנו.

### מסד הנתונים

`supabase/migrations/0001_card_state.sql` — טבלת `card_state` להיסטוריה,
ו-`review_log` ליומן החזרות. RLS מגביל כל משתמש לשורות שלו.

מיגרציות רצות ידנית ב-SQL Editor של Supabase, לפי הסדר. **`0006_sync_and_admin.sql`
צריכה לרוץ לפני שמיזוג ל-main מגיע למשתמשים**: היא נותנת ל-`user_id` ברירת מחדל,
מוסיפה שומרי סדר (מכשיר ישן לא דורס מצב חדש), מזהה ייחודי ליומן החזרות, את
בקרת החבילות הציבוריות ואת פעולות האדמין. הלקוח עובד גם לפניה — יומן החזרות
פשוט ממתין במכשיר עד שהיא רצה, ומסך הניהול מבקש להריץ אותה.

`0007_merge_and_purge.sql` — רק פונקציות: `merge_decks` (איחוד נושאים) ו-`admin_purge_decks`
(מחיקה מלאה בידי אדמין). בלעדיה האיחוד מבקש להריץ אותה, ומחיקה באדמין נופלת
למחיקה רגילה שמשאירה את ההתקדמות יתומה בשרת.

### מטמון מקומי וסנכרון

מקור האמת הוא Supabase. המכשיר מחזיק מראה, כדי שהאפליקציה תעלה מיד ותעבוד
בלי רשת. כל מה שמשויך למשתמש נשמר במפתח עם ה-uid שלו (`shinun-cards:<uid>`),
כך שמשתמש שני באותו מכשיר לא רואה את הראשון, והתנתקות לא מוחקת תרגול שלא נשלח.

| מפתח | מה | מתי נשלח לשרת |
|---|---|---|
| `shinun-cards` | מצב FSRS לכל כרטיס — מה שהמתזמן קורא | — |
| `shinun-dirty` | כרטיסים שהשרת עוד לא אישר | שורה אחת לכל כרטיס, נבנית מהמצב האחרון |
| `shinun-log` | יומן חזרות, כל רשומה עם מזהה משלה | שליחה חוזרת לא מכפילה (`client_id`) |
| `bio-quiz-v2` | תאריך מבחן וסבבים, עם זמן השינוי | שינוי מקומי שלא נשלח לא נדרס במשיכה |
| `shinun-rows` | מראה של הספרייה, לאופליין | — (נמשך מהשרת) |
| `shinun-why` | הסברי "למה?" — לפי כרטיס ותשובה שנבחרה | — |
| `shinun-errq` | תקלות שממתינות ליומן בשרת | עם המשתמש והזמן שבהם קרו |
| `shinun-auth` | המפגש (טוקנים, uid) | — |

הכלל בכרטיסים: החזרה המאוחרת מנצחת, בשני הכיוונים — גם בלקוח וגם בשרת
(`card_state_guard`). הסנכרון רץ לבד: בעלייה, בחזרה לאפליקציה, כשהרשת חוזרת,
אחרי תשובות, ובניסיונות חוזרים במרווחים אחרי כישלון. אין כפתור רענון או איפוס
של המטמון — אין בו צורך.

### אדמין

אדמין מוגדר לפי מייל בטבלה `admin_emails` (מ-0006; ההרשאה ניתנת ברגע שהמייל
מאומת). כפתור "ניהול" במסך הבית מוביל ל:

- **לאישור** — נושאים שמשתמשים פרסמו. פרסום של משתמש רגיל לא מופיע לאחרים עד
  אישור; עריכה של נושא מאושר מחזירה אותו לתור, ומי שכבר רשום ממשיך לראות אותו.
  תצוגה מקדימה, אישור, דחייה עם הערה לבעלים, ומחיקה.
- **ציבוריות** — כל מה שבמאגר: הסתרה או מחיקה לצמיתות — הנושא, המנויים אליו
  וההתקדמות של כל מי שתרגל אותו. "מחק את כולם לצמיתות" תופס כל נושא ציבורי
  (מאושר או ממתין) של משתמשים אחרים; הנושאים של האדמין עצמו לא נכללים.
- **משתמשים** — מי פעיל, וכמה כרטיסים שלו באמת הגיעו לשרת.
- **יומן תקלות** — עם המייל והגרסה של המדווח, דפדוף, מחיקת המוצגים וניקוי ישנים.
- **מערכת** — מצב המכשיר הזה (מה ממתין לשליחה) וסנכרון יזום.

אדמין נוסף: `insert into public.admin_emails (email) values ('...')` ב-SQL Editor.

פרויקט Supabase חינמי מושהה אחרי כשבוע בלי פעילות. `.github/workflows/keep-alive.yml`
שולח שאילתה קטנה פעם ביום כדי למנוע זאת; ריצה אדומה שם פירושה שהפרויקט
כנראה כבר מושהה, ויש לשחזר אותו מלוח הבקרה של Supabase.

### איחוד נושאים

במאגר הנושאים, "אחד": בוחרים נושא יעד משלך ומסמנים מה לצרף אליו — נושאים שלך
או של אחרים, מאותו סוג (עץ האיזומרים לא מתאחד: יש בו הפניות בין פריטים).
הכול קורה בשרת בטרנזקציה אחת (`merge_decks`):

- פריט שכבר קיים ביעד בדיוק כמו שהוא — לא מוכפל. אותו id עם תוכן אחר — נשמר
  כ-`x-2` וכן הלאה, כל אחד עם ההיסטוריה שלו.
- ההתקדמות עוברת למפתח החדש. כמה מקורות לאותו כרטיס — נשאר זה עם החזרה המאוחרת.
- נושא שלך שצורף — נמחק, והמנויים שלו עוברים ליעד אם הוא ציבורי. יעד ציבורי של
  משתמש רגיל חוזר לאישור, כמו בכל עריכה.
- נושא של אחר — הכרטיסים מועתקים, רק ההתקדמות שלך עוברת, והמינוי שלך אליו מוסר.

## הוספת חבילה חדשה

הכול ב-`src/app.html` (והתוכן המוטמע ב-`data/decks.json`):

1. מוסיפים מערך דאטה (כמו `GROUPS` / `ELEMENTS` / `ISO`).
2. כותבים בונה שאלות שמחזיר `{key, label, prompt, optionKind, options, answer, why}`.
3. מוסיפים רשומה ל-`DECKS` עם `modes` ו-`build(mode)`.

`prompt.kind` הנתמכים: `mol` (מבנה), `text`, `element` (סמל גדול), `pair` (שני מבנים).
`optionKind`: `text` או `pic`.

## תרגילים אינטראקטיביים

נושא (`kind: topic`) יכול להכיל, לצד הכרטיסים, תרגילי שיבוץ: בנק תשובות,
והמשתמש מקיש על פריט ואז על המקום שלו (או גורר בעכבר). פריט עם `type` הוא תרגיל.

```js
/* מיון לקבוצות. קבוצה עם פריט יחיד = התאמה אחד־לאחד */
{ id:'aa-side-chains', type:'sort', prompt:'מיין לפי השרשרת הצדדית',
  groups:[{label:'ארומטיות', sub:'Aromatic', items:['Phe','Tyr','Trp']}, ...],
  extra:['...'],            // מסיחים שלא שייכים לשום קבוצה — רשות
  note:'...' }

/* רצף, או מעגל כש-cycle. arrow = מה שעל החץ שיוצא מהשלב אל הבא */
{ id:'krebs-enzymes', type:'order', cycle:true, ask:'arrows',
  prompt:'שבץ את האנזים של כל שלב',
  steps:[{label:'אוקסלואצטט', sub:'Oxaloacetate', arrow:'Citrate synthase'}, ...] }
```

`ask` קובע מה ממלאים: `steps` (ברירת מחדל, החיצים מוצגים כרמז), `arrows`, או `both`.
`given:true` משאיר שלב גלוי; מעגל בלי עוגן חושף את השלב הראשון. מעגל של עד
עשרה שלבים מצויר כעיגול, ארוך יותר — כרשימה.

כל תרגיל הוא כרטיס אחד בתזמון. הציון נגזר מחלק השיבוצים הנכונים: מושלם — 3
או 4 לפי מהירות לפריט, 80% ומעלה — 2, פחות — 1. ההשוואה לפי טקסט, כך ששני
חיצים שמצפים ל-NADH מקבלים כל אחד מהעותקים.

תרגיל אחד מספיק לנושא; כרטיסים נכנסים לסבב רק מארבעה ומעלה. הצ'אט
(`add-question`) מכיר את הסכימה ובונה תרגילים כשמבקשים "מיון", "שיבוץ",
"סדר את" או "השלם את המעגל".

## מנוע ציור המולקולות

מולקולה = אטומים בקואורדינטות רשת + קשרים בין אינדקסים.

```js
{ a:[A('R',0,1), A('C',1,1), A('O',1,2)],
  b:[[0,1,1], [1,2,2]] }
```

סוגי קשר: `1` יחיד · `2` כפול · `3` טריז (קדימה מהמישור) · `4` מקווקו (אחורה).
צבע האטום נגזר מהיסוד. אורך הקשר מחושב לפי גבול תיבת התווית, כך שתוויות ארוכות
(`OH`, `CH₂OH`) לא בולעות את הקו.

## התקנה בטלפון בלי APK

`npm run serve`, פותחים בטלפון את הכתובת שמודפסת, ובכרום: תפריט ← התקנת אפליקציה.
מקבלים אייקון, מסך מלא ועבודה אופליין (service worker).
